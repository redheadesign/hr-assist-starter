# Что публикуется и что остаётся локально

В Git допускаются только перечисленные в `.release-allowlist` текстовые файлы: код, правила, документация, пустые шаблоны и синтетические тесты. Личные настройки не записываются в эти шаблоны. Новое правило публикации добавляй только после просмотра всего файла.

`.local/` содержит профиль, контакты, документы, фото, сообщения, базы, отчёты и состояние онбординга. Она исключена из Git целиком. Приватный репозиторий также не подходит для хранения OAuth-токенов, cookies, паролей и кодов входа. Для секретов используй штатное защищённое хранилище интеграции вне проекта.

## Перед первым и каждым следующим push

1. Прочитай `git status --short` и `git diff --cached`.
2. Проверь каждый новый файл целиком: имена, контакты, ссылки на личные профили, суммы, работодатели из личной истории, документы и тексты переписок. Проверь также метаданные коммитов.
3. Выполни `python scripts/privacy_guard.py --index --history`. Проверка читает подготовленные версии файлов и все достижимые коммиты, включая удалённые впоследствии файлы.
4. При необходимости передай `--denylist <внешний JSON-файл>` с приватными строками. Этот список нельзя публиковать.
5. Убедись, что удалённый репозиторий приватный. Не полагайся только на название или прошлое состояние.

Проверка не является DLP-системой и не распознаёт любые персональные данные. Разрешённый список ограничивает состав, регулярные выражения ищут типичные утечки, ручной просмотр закрывает контекстные случаи. Не ослабляй проверку только ради успешного push.

Можно включить дополнительную локальную проверку перед push: `git config --local core.hooksPath .githooks`. Это меняет только настройки данного клона. Hook требует команду `python` в PATH; он не является защитой от намеренного обхода и не устанавливается автоматически.

Для обезличенного шаблона используй нейтральные имя/почту автора коммитов (например, `Template Maintainer` и `maintainer@example.invalid`). История Git также передаётся на сервер. GitHub может отдельно записать владельца и действие отправки; это свойство аккаунта, не содержимое шаблона.

## Восстановление с нуля

Клонируй репозиторий, установи зависимости и запусти `scripts/setup.py init`. Скрипт создаёт все пустые таблицы JSONL, каталоги и версию схемы. SQL-сервер не нужен.

`init` повторяемый: заполненные файлы не заменяет. Неизвестную версию схемы отклоняет, без удаления данных. Будущие изменения схемы требуют отдельной миграции и локальной резервной копии, а не пересоздания базы.

Если нужно восстановить личную историю, останови записи, сделай отдельный зашифрованный архив `.local` и передавай его отдельно от Git. Для нового клона восстанови архив в `.local`, запусти `setup.py status` и `hr_store.py validate`. Не храни ключ шифрования рядом с архивом. Аккаунты и расписания подключай заново: браузерные сессии и задания не переносятся клонированием.

Если приватный файл уже попал в коммит, `.gitignore` недостаточно. Останови отправку, оцени, был ли он опубликован, отзови утёкшие секреты и отдельно согласуй очистку истории по [документации GitHub](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository). Не переписывай рабочую историю пользователя без разрешения.
