# Ошибки адаптивного монитора

Этот контракт применяется до браузерных действий и при любом исходе запуска. Очередь probes не является разрешением на постоянный частый cron. Рабочие файлы находятся в корне личного проекта, в starter внутри `.local`.

1. Получи краткий hr_context bot-monitor и retry_guard. При may_scan=false не открывай браузер и не запускай диагноста. Сверь фактическое расписание существующего монитора, установи интервал не меньше interval_minutes_floor и закончи запуск. Сохрани модель, проект и уведомления; не включай задание, приостановленное владельцем, без его поручения.
2. Если просмотр разрешён, **до обращения к браузеру** установи существующему заданию безопасный интервал unfinished_retry_minutes (по умолчанию 240 минут) штатным automation_update. Прочитай результат. При неудаче изменения не начинай браузерный просмотр: попытайся приостановить это же задание и один раз сообщи ограничение. Не оставляй быстрый cron для повторения той же ошибки.
3. Выполни hr_monitor_guard.py begin --attempt-key KEY. KEY уникален для запуска и повторно используется при повторе записи. Продолжай только при scan_authorized=true. Guard заранее сохраняет срок допустимого повтора, чтобы обрыв процесса не выглядел новым разрешением на скан. Пустая очередь не отменяет положенный редкий просмотр входящих, но промежуточный тик без due-чата, due-probe и без наступившего общего inbox-интервала не должен читать сайты: пересчитай расписание и закончи.
4. Для HH сразу открой `https://hh.ru/chat` штатным браузерным инструментом. Не начинай с главной или списка откликов. Для проверки конкретного нового сообщения выбери наблюдённый чат из этого списка. В CUA js укажи timeout_ms=60000; не полагайся на 30-секундный default. Пользовательский браузер может работать при таймауте инструмента. Ошибка `js execution timed out; kernel reset` доказывает сброс выполнения CUA, а не зависание HH. Не меняй видимость профиля и не обходи CAPTCHA/login.
5. Сохрани компактное доказательство исхода. При ошибке или неполном просмотре вызови finish --attempt-key KEY --outcome error --error-code CODE --artifact-ref REF. Ошибка не продвигает checkpoint сообщений и полного импорта. Уже наступившие probes закрой одной попыткой ack-probe с outcome=error; не создавай их заново. Повторное finish того же KEY идемпотентно. Guard назначает паузу 240, затем 480, затем максимум 1440 минут при последовательных неудачах. Активный чат и просроченные probes не обходят эту паузу.
6. Только после записи ошибки разрешена одна диагностика на непрерывный эпизод сбоев: hr_monitor_guard.py diagnose --attempt-key KEY резервирует её до запуска агента. Только при diagnostic_authorized=true отправь короткий пакет Sol high, fork_turns=none: точный URL, вызов, timeout, дословная ошибка, наблюдённые признаки, путь артефакта. Не передавай переписку, биографию и всю историю; не разрешай внешнюю отправку или изменение проекта. Диагност не делегирует дальше, максимум одна попытка чтения и объяснение/следующий шаг. Отсутствие доступного Sol или согласия на делегацию оставляет паузу. Astra не используется. Повторные тики того же эпизода не запускают новых диагностов; смена формулировки ошибки не сбрасывает лимит. Диагноз не считается успешным мониторингом и не снимает паузу.
7. При полном успешном просмотре вызови finish --outcome success с тем же KEY и артефактом, сохрани только реально прочитанные checkpoints, закрой наступившие probes. Успех сбрасывает последовательные ошибки. На обоих исходах перечитай guard и schedule-mode, примени max(расчётный интервал, interval_minutes_floor) к реальному заданию через automation_update. Если run_now=true после ошибки, приоритет у guard, немедленный повтор запрещён. После успеха обслужи действительно появившуюся работу и пересчитай режим, а не устанавливай нулевой интервал.

Guard хранит время попытки отдельно от времени успешного чтения. Это позволяет отложить неудачную проверку и сохранить непрочитанные сообщения для следующего запуска. Штатные скрипты сами не меняют планировщик: реальный безопасный интервал до браузера обязателен, запись JSON его не заменяет. Не возобновляй старый четырёхминутный режим по заметке memory.md: текущая инструкция и состояние guard имеют приоритет. Проверяй различия фактического расписания даже при пустой очереди.
